# Next.js, App Router, server-rendered, on Node 24

Date: 2026-08-30
Status: accepted

## Context

The panel shows a fleet that changes while the operator is looking at it, on
their own machine, distributed by cloning the repository and running it.

## Decision

Node 24, TypeScript, ESM. Next.js App Router, server-rendered, built with
`output: "standalone"`. React with small client islands only. Tailwind and
shadcn/ui. Tests with `node:test`, behavioural, against the built output.
Package name `quarterdeck-axi`.

## Why this, and what it costs

**Server rendering with a data-free refresh signal** is the choice everything
else follows from. The alternative - a client app fetching JSON and rebuilding
the page - is the standard shape, and it is the one that makes cards flicker,
collapses an expanded panel, and jumps the scroll at the moment the operator is
reading. Rendering on the server and letting React reconcile the returned markup
keeps the page still. The cost is that every update is a round trip, which is
free on loopback and would not be over a network.

**Next specifically**, rather than a hand-rolled server, buys the streaming
render, the island boundary and the build with no assembly. The cost is a large
dependency for a local tool, and a framework that moves: this task already hit
`middleware.ts` being renamed to `proxy.ts`. That churn is the price.

**`node:test` against the built output**, not a test framework against source.
Testing the build is what stops a green suite from describing code nobody runs;
the cost is slower tests, since each behavioural test starts a server.

**Node 24** strips TypeScript types natively, so `bin/quarterdeck` imports the
port derivation from `src/` directly rather than duplicating it or compiling a
second output. The cost is a hard floor on the Node version, declared in
`engines`.

**No publishing machinery.** Clone and run. Nothing to release means nothing to
version, and the panel reads a private fleet, so a registry is the wrong shape.
